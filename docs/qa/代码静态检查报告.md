## 一、安全问题

### [🔴] ✅ JWT Secret 硬编码兜底值，三处重复
- 文件：`backend/src/auth/auth.module.ts:18`、`backend/src/auth/strategies/jwt.strategy.ts:12`、`backend/src/auth/guards/jwt-auth.guard.ts:37`
- 描述：JWT secret 曾写为 `process.env.JWT_SECRET || 'ai_teacher_jwt_secret_2026'`（本条为历史检查记录；现已全部移除兜底值，`main.ts` 启动强制校验 ≥32 位，auth/wechat 各处均为无兜底写法）。
- 影响：任何人知道这个硬编码字符串就能伪造任意用户的 JWT token（包括 super_admin），完全绕过认证。
- 建议：删除兜底值，启动时强制校验 `process.env.JWT_SECRET` 存在且长度 ≥ 32；在 `.env` 和 docker-compose.prod.yml 中配置强随机密钥。

### [🔴] ✅ CORS 完全开放
- 文件：`backend/src/main.ts:24`
- 描述：`app.enableCors()` 未传入任何配置，等价于 `origin: '*'`，允许任意域名跨域请求后端 API。
- 影响：恶意网站可在用户登录后携带其 Cookie/Token 发起跨域请求，结合前端 localStorage 中的 token，可被 CSRF/数据窃取利用。
- 建议：配置白名单 `app.enableCors({ origin: ['https://admin.your-domain.com'], credentials: true })`。

### [🔴] ✅ 用户更新接口缺失角色守卫，存在垂直越权提权
- 文件：`backend/src/users/users.controller.ts:46-49`
- 描述：`@Put(':id')` 方法没有 `@Roles()` 装饰器。类级别有 `@UseGuards(JwtAuthGuard, RolesGuard)`，但 RolesGuard 在没有 `@Roles()` 时直接放行（roles.guard.ts:14 `if (!requiredRoles) return true`）。
- 影响：任何已登录用户（包括 teacher）都可以调用 `PUT /users/:id`，传入 `{role: 'super_admin'}` 将自己提权为超级管理员。也可以修改其他用户的任意字段。
- 建议：给 `@Put(':id')` 加上 `@Roles('super_admin')`（学校管理员只能改本校普通用户，不能改角色字段）。

### [🔴] ✅ 用户查看接口缺失角色守卫，水平越权读取
- 文件：`backend/src/users/users.controller.ts:41-44`
- 描述：`@Get(':id')` 方法没有 `@Roles()` 装饰器。
- 影响：任何已登录用户可遍历用户 ID 查看所有用户的邮箱、电话、学校归属等信息。
- 建议：加上 `@Roles('super_admin', 'school_admin')`，并在 service 层校验只能查看本校用户。

### [🔴] ✅ 设备注册接口完全无认证，可任意绑定设备到学校
- 文件：`backend/src/boxes/boxes.controller.ts:11-15`、`backend/src/boxes/boxes.service.ts:8-17`
- 描述：`POST /boxes/register` 没有任何 `@UseGuards`，接收 `serialNumber` 和 `schoolId` 直接写入数据库。
- 影响：攻击者可批量注册恶意设备序列号到任意学校，污染设备管理数据；后续心跳接口也无认证，可伪造在线状态。
- 建议：注册接口应使用预共享密钥（device provisioning token）或由 super_admin/school_admin 在后台手动注册，设备首次联网时通过密钥激活。

### [🔴] ✅ 设备心跳接口无认证，可伪造设备状态
- 文件：`backend/src/boxes/boxes.controller.ts:17-21`、`backend/src/boxes/boxes.service.ts:20-35`
- 描述：`POST /boxes/heartbeat/:serial` 无认证，任何人可对任意 serialNumber 发送心跳，将设备标记为 online 或 error。
- 影响：攻击者可批量将所有设备标记为故障，触发虚假告警；或将故障设备"心跳"恢复为在线，掩盖真实故障。
- 建议：设备端心跳应携带注册时分配的 device token，服务端校验 token + serialNumber 配对。

### [🔴] ✅ 密码更新未经过哈希，明文存储
- 文件：`backend/src/users/users.service.ts:38-40`
- 描述：`update(id, data)` 直接将 `data` spread 传给 `prisma.user.update()`。如果客户端发送 `{password: 'newpass'}`，密码以明文入库。
- 影响：数据库泄露时所有密码明文暴露；且与登录时 `bcrypt.compare` 不匹配，用户改密后无法登录。
- 建议：在 service 层检测 `data.password`，若存在则先 `bcrypt.hash()` 再传入；禁止直接 spread body。

### [🔴] ✅ 登录接口无失败次数限制 / 无验证码
- 文件：`backend/src/auth/auth.service.ts:14-25`、`backend/src/auth/auth.controller.ts:10-13`
- 描述：登录接口仅校验用户名密码，没有失败计数、账号锁定、验证码或 IP 限流。
- 影响：攻击者可对 `/auth/login` 进行无限制暴力破解。
- 建议：接入 `@nestjs/throttler`，对登录接口限制 5 次/分钟；连续失败 5 次锁定 15 分钟。

## 二、逻辑 Bug 和边界条件

### [🟡] ✅ tutoring.listDevices 中 where 条件 type 键重复，筛选被覆盖
- 文件：`backend/src/tutoring/tutoring.service.ts:110`
- 描述：`where: { schoolId, ...(type ? { type } : {}), type: { in: ['glasses', 'watch'] } }` 对象字面量中 `type` 键出现两次，后者覆盖前者。前端传入的 `type` 查询参数完全无效。
- 影响：穿戴设备列表永远只返回 glasses + watch 类型，无法按 glasses/watch 单独筛选。
- 建议：改为 `where: { schoolId, ...(type ? { type } : { type: { in: ['glasses', 'watch'] } }) }`。

### [🟡] ✅ 请假审批无状态校验，并发重复审批
- 文件：`backend/src/leaves/leaves.service.ts:23-34`
- 描述：`approve()` 先 `findUnique` 查出 leave，但未检查 `leave.status === 'pending'`。两个管理员同时点审批会重复更新。
- 影响：重复审批覆盖 reviewerId，业务审计混乱。
- 建议：update 时加条件 `where: { id, status: 'pending' }`，根据 update.count 判断是否已被处理。

### [🟡] ✅ 课后打分重复调用会产生重复 Evaluation 记录
- 文件：`backend/src/evaluations/evaluations.service.ts:15-64`
- 描述：`scoreAfterLesson()` 对每个学生直接 `create` Evaluation，没有检查该 lessonRecordId + studentId 是否已存在。
- 影响：手动或定时任务重复触发会产生重复评分记录，污染平均分和排名。
- 建议：create 前先 `findFirst` 检查，或使用 `upsert`。

### [🟡] ✅ 多步写操作未使用事务
- 文件：`backend/src/tutoring/tutoring.service.ts:24-54`、`backend/src/subscriptions/subscriptions.service.ts:79-84`
- 描述：`subscribe()` 中先更新两个 device，再 upsert subscription，三步无事务；`disable()/enable()` 中先更新 school 再更新 subscription，两步无事务。
- 影响：中间步骤失败会导致数据不一致（如设备已绑定但订阅未创建，或学校已禁用但订阅仍 active）。
- 建议：使用 `prisma.$transaction([...])` 包裹多步写操作。

### [🟡] ✅ 外键删除无级联，删除学生/学校/班级会失败
- 文件：`backend/prisma/schema.prisma`（Student 模型 relations）、`backend/src/students/students.service.ts:30-32`
- 描述：Student 关联了 Parent、Attendance、Evaluation、Score、Submission、Leave、Warning 等 16 张子表，仅 FacePhoto 设置了 `onDelete: Cascade`，其余均为默认 Restrict。
- 影响：调用 `DELETE /students/:id` 时，只要该学生有任何考勤/成绩/请假记录，就会抛 P2003 外键约束错误，无法删除。删除 School/Grade/Class 同理。
- 建议：对学生采用软删除（status 改为 inactive）；或在 schema 中对子表设置 `onDelete: Cascade`，或在 service 中先删子表再删主表并包在事务里。

### [🟡] ✅ 辅导会话开始时不关闭已有 active 会话
- 文件：`backend/src/tutoring/tutoring.service.ts:128-143`
- 描述：`startSession()` 直接创建新 session，未检查该学生是否已有 status='active' 的旧会话。
- 影响：同一学生可存在多个 active session，chat/end 操作可能错乱，统计时长重复计算。
- 建议：创建前先 `updateMany` 将该学生所有 active session 标记为 ended。

### [🟡] ✅ cancelSubscription 未检查记录是否存在
- 文件：`backend/src/tutoring/tutoring.service.ts:85-90`
- 描述：直接 `update({ where: { studentId } })`，若该学生没有订阅记录会抛 P2025，被全局 filter 转为 404，但错误信息不友好。
- 影响：重复取消或取消未开通的学生返回 500/404，无明确提示。
- 建议：先 findUnique 检查，不存在则抛 BadRequestException。

## 三、性能问题

### [🟡] ✅ 学生报告中 N+1 查询：为每个学生单独查 Evaluation
- 文件：`backend/src/evaluations/evaluations.service.ts:123-129`
- 描述：`studentReport()` 中，对班级内每个学生执行一次 `evaluation.findMany()`。50 人班级 = 50 次额外查询。
- 影响：班级越大越慢，数据库连接池容易被打满。
- 建议：一次性 `evaluation.findMany({ where: { studentId: { in: studentIds } } })`，在内存中分组。

### [🟡] ✅ schoolHealth 中 N+1：为每所学校循环查询 10+ 次
- 文件：`backend/src/dashboard/dashboard.service.ts:176-245`
- 描述：对 schools 数组做 `map`，每所学校内部串行查询 boxes、workOrders(3次)、schedule、students、classes、grades、parents、messages(2次)、tutoring(2次) = 约 11 次查询。
- 影响：100 所学校 = 1100 次数据库查询，接口响应极慢。
- 建议：改用 `groupBy` 聚合查询，或批量 `in` 查询后在内存分组。

### [🟡] ✅ 跨校排名加载全量学生画像到内存
- 文件：`backend/src/rankings/rankings.service.ts:116-119`
- 描述：`crossSchoolRanking()` 无分页 `findMany`，include 嵌套 student→class→grade→school，加载所有学校所有学生画像。
- 影响：学生数达到数万时内存溢出、响应超时。
- 建议：按 school.city/province 筛选，使用数据库 `rank()` 窗口函数而非全量加载后 JS 排序。

### [🟡] ✅ globalOverview 加载全量学校+年级+班级+学生
- 文件：`backend/src/dashboard/dashboard.service.ts:126-131`
- 描述：`school.findMany()` include grades → classes → students（全量 students 数组），所有学校一次性加载。
- 影响：学校数量增长后内存占用线性膨胀。
- 建议：学生数改用 `_count.students` 聚合，不要 include 全量 students。

### [🟡] ✅ UsageLog 用量统计全量加载到内存聚合
- 文件：`backend/src/dashboard/dashboard.service.ts:266-269`
- 描述：`usageLog.findMany()` 查询 30 天所有 llm_api 日志到内存，再 JS 循环聚合。
- 影响：日志量大时内存和 CPU 压力大。
- 建议：使用 Prisma `groupBy` + `aggregate` 在数据库端聚合。

### [🟡] ✅ 数据库索引严重缺失
- 文件：`backend/prisma/schema.prisma`
- 描述：仅 WorkOrder 和 FacePhoto 定义了 `@@index`。以下高频 WHERE/JOIN 字段均无索引：
  - `Student.classId`（按班级查学生）
  - `Submission.assignmentId`、`Submission.studentId`（作业提交列表）
  - `Score.examId`、`Score.studentId`（考试成绩）
  - `Leave.studentId`、`Leave.status`（请假列表）
  - `Attendance.lessonRecordId`、`Attendance.studentId`（考勤）
  - `Evaluation.lessonRecordId`、`Evaluation.studentId`（课堂评估）
  - `Schedule.schoolId`、`Schedule.classId`、`Schedule.startTime`（课表）
  - `Box.schoolId`（设备列表）
  - `TutoringSession.studentId`（辅导历史）
- 影响：数据量增长后查询全表扫描，响应时间急剧恶化。
- 建议：为所有外键和高频过滤字段添加 `@@index`。

### [🟡] ✅ 多个列表接口无分页
- 文件：`backend/src/boxes/boxes.service.ts:63-73`、`backend/src/leaves/leaves.service.ts:38-43`、`backend/src/evaluations/evaluations.service.ts:161-165`
- 描述：`findBySchool`、`pending`、`warnings` 等均为 `findMany()` 无 take/skip。
- 影响：学校设备/请假/学生数量大时一次性返回全量数据。
- 建议：统一加分页参数 page/pageSize。

### [🟡] ✅ 文件上传无大小限制和类型限制
- 文件：`backend/src/textbooks/textbooks.controller.ts:13`、`backend/src/face-library/face-library.controller.ts:16`、`backend/src/assignments/assignments.controller.ts:81`
- 描述：`FileInterceptor('file')` 未配置 `limits`（如 `fileSize: 10MB`）和 `fileFilter`。
- 影响：用户可上传超大文件耗尽服务器磁盘/内存；可上传可执行文件。
- 建议：配置 `FileInterceptor('file', { limits: { fileSize: 20*1024*1024 }, fileFilter })`。

## 四、错误处理

### [🟡] ✅ 全局异常过滤器不记录错误日志
- 文件：`backend/src/common/filters/all-exceptions.filter.ts:26-40`
- 描述：对于非 HttpException 的 500 错误（Prisma 错误、运行时异常），直接返回"服务器内部错误"，没有 `console.error` 记录原始堆栈。
- 影响：生产环境出现 500 时无法排查根因。
- 建议：在 catch 块中 `console.error(exception)` 记录完整堆栈，再返回通用错误信息。

### [🟡] ✅ textbooks.parse 临时文件清理在 try 块内，异常时不清理
- 文件：`backend/src/textbooks/textbooks.service.ts:67-137`
- 描述：`fs.rmSync(tmpDir, ...)` 在 try 块末尾（第 124 行），如果 OCR 脚本抛异常跳到 catch 块，临时文件不会被删除。
- 影响：/tmp 目录残留大量 OCR 临时文件，长期运行占满磁盘。
- 建议：将 `fs.rmSync` 放入 `finally` 块。

### [🟢] ✅ P2002 唯一约束错误泄露字段名
- 文件：`backend/src/common/filters/all-exceptions.filter.ts:37-38`
- 描述：`message = \`数据已存在（${target}）\`` 将数据库唯一约束字段名返回给前端。
- 影响：轻微信息泄露，攻击者可得知表结构。
- 建议：生产环境只返回通用提示"数据已存在"，不暴露 target 字段。

### [🟢] ✅ 大量 DTO 使用 `any` 类型，class-validator 装饰器缺失
- 文件：`backend/src/users/users.controller.ts:15,47`、`backend/src/assignments/assignments.controller.ts:32,69`、`backend/src/textbooks/textbooks.controller.ts:16`
- 描述：全局 ValidationPipe 配置了 `whitelist: true, transform: true`，但多数 DTO 直接用 `@Body() body: any`，没有定义 class-validator 装饰器。
- 影响：无法在请求入口校验必填字段、类型、范围；脏数据直接进库。
- 建议：为每个 POST/PUT 定义 DTO class，加上 `@IsString() @IsNotEmpty() @IsOptional()` 等装饰器。

## 五、前后端契约

### [🟡] ✅ 前端 baseURL 硬编码 localhost
- 文件：`admin-web/src/utils/request.ts:5`
- 描述：`baseURL: 'http://localhost:3000/api/v1'` 硬编码。
- 影响：打包后部署到任何非本机环境都无法连接后端。
- 建议：改为 `baseURL: import.meta.env.VITE_API_BASE_URL || '/api/v1'`。

### [🟢] 响应格式契约一致
- 后端 `TransformInterceptor` 返回 `{code: 0, data, message: 'success'}`，异常 filter 返回 `{code: 非0, data: null, message}`。
- 前端 `request.ts:20-24` 判断 `res.code !== 0` 则报错，否则返回 `res.data`。
- 结论：✅ 前后端契约一致。

### [🟢] 角色枚举对齐
- 后端 schema 注释：`super_admin, group_admin, school_admin, grade_admin, subject_admin, teacher`
- 前端 router guard：`grade_admin, subject_admin, teacher` 被拦截访问 schoolOnly 页面。
- 结论：基本对齐，但 `group_admin` 在前端路由 guard 中未处理（RolesGuard 已将其映射为 super_admin，但前端 localStorage 中 role 若为 group_admin，不会被 schoolOnly 拦截）。

## 六、前端问题

### [🟢] ✅ 路由守卫仅检查 token 存在性，不校验过期
- 文件：`admin-web/src/router/index.ts:46-64`
- 描述：`beforeEach` 只判断 `localStorage.getItem('admin_token')` 是否存在，不解析 JWT 过期时间。
- 影响：token 过期后用户停留在页面上，直到下一个 API 请求返回 401 才跳转登录。
- 建议：在 guard 中解码 JWT 的 exp 字段，过期则直接清 token 跳登录。

### [🟢] ✅ teacher 可访问多个管理页面（前端未拦截，后端 API 兜底）
- 文件：`admin-web/src/router/index.ts:15-36`
- 描述：teacher 角色仅被拦截 schoolOnly 页面，但 schools、leads、subscription、work-orders、health 等 super_admin 专属页面对 teacher 仍可见。
- 影响：UI 体验差（点进去才报 403），但后端有 RolesGuard 兜底，不构成安全漏洞。
- 建议：在路由 meta 中加 `roles: ['super_admin']`，guard 中按角色过滤菜单。

### [🟢] 无 v-html 使用，无 XSS 风险
- Grep 结果：admin-web/src 下无 `v-html`。
- setInterval/setTimeout 均在 onUnmounted 中清理（layout/index.vue:188, login/index.vue:192）。

## 七、配置和部署

### [🟡] ✅ Swagger API 文档在生产环境暴露
- 文件：`backend/src/main.ts:27-34`
- 描述：`SwaggerModule.setup('api/docs', app, document)` 无环境判断，生产环境也可访问。
- 影响：攻击者可浏览全部 API 接口、参数、返回格式，降低攻击成本。
- 建议：仅在 `NODE_ENV !== 'production'` 时启用 Swagger。

### [🟡] ✅ Docker 后端服务无 healthcheck
- 文件：`infra/docker/docker-compose.prod.yml:77-101`
- 描述：postgres 有 healthcheck，但 backend 和 redis 均无 healthcheck。
- 影响：docker orchestrator 无法判断后端是否真正就绪，重启策略可能误判。
- 建议：backend 加 `healthcheck: test: ["CMD", "curl", "-f", "http://localhost:3000/api/v1/health"]`。
